## Existing architecture retained

The following mature 3.0.2 behaviors were retained rather than replaced:

- shared `TravelEngine` warmup/cooldown/economy/safe-teleport pipeline;
- asynchronous RTP chunk acquisition and bounded search attempts;
- uniform-area ANNULUS sampling;
- world-border enforcement;
- `generate-chunks: false` default behavior;
- SQLite destination/warp/back persistence and existing schema;
- per-world spawn/hub lookup with legacy fallback;
- internal-teleport tracking used to protect external `/back` capture;
- TPA request lifecycle;
- PlaceholderAPI/Core integration;
- phase-aware startup diagnostics and real Paper startup smoke gate;
- command-takeover and migration safety controls.

## 3.1 architecture decisions

### World settings

A dedicated `world-settings.yml` owns explicit 3.1 per-world RTP and void-rescue rules. World UUID is the durable key; the last-known world name is retained for operator readability. Effective runtime rules are immutable/cached and are replaced transactionally after validation and successful persistence.

### RTP

RTP was extended through boundary/profile abstractions instead of duplicating the search engine. ANNULUS, RECTANGLE, and WORLD_BORDER resolve to bounded sampling strategies, all constrained by the active Minecraft world border. Worlds without an explicit 3.1 RTP rule inherit the existing 3.0.x global configuration.

### Void rescue

Void rescue is a dedicated focused listener/service. It does not dispatch player commands and does not use ordinary paid/warmup travel semantics. It deduplicates active rescues, applies failure backoff, uses cached world rules, ignores horizontal-only movement, and marks rescue teleports internal so `/back` is not polluted by the void source.

## Compatibility conclusions

- No SQLite schema migration is required.
- Existing 2.x/3.x persistent travel data remains readable.
- Existing 3.0.2 `config.yml` remains valid.
- Existing `rtp.*` fields are not deleted or silently reinterpreted.
- The new `world-settings.yml` is additive, allowing rollback to 3.0.2 without destructive data conversion.
- Existing player commands remain available with their established permission nodes.
- New RTP/void administration is isolated under `plexontravel.admin.rtp` and `plexontravel.admin.void`.

## Performance conclusions

The 3.1 design introduces no movement-event filesystem, YAML parsing, or SQL access. Void rescue short-circuits movement without Y change and uses one in-flight state per player. RTP remains bounded, asynchronous for chunk acquisition, and does not synchronously generate terrain by default.

## Release boundary

GitHub CI/Paper startup smoke proves source/build/startup integrity. Live PlexonCraft movement, RTP-boundary behavior, void rescue, `/back` preservation, and production TPS/MSPT remain a separate runtime certification boundary. They must not be reported as live PASS without host evidence.
